# 微信公众号日常排版规则

本文件规定日常微信公众号文章的固定排版行为。除非用户在本次请求中明确提出不同要求，否则必须按本文件执行；用户本次明确要求优先。

## 1. 默认主题

所有日常微信公众号文章，除非用户明确指定其他主题，否则默认使用正式主题：

`蓝白色系（blue-white）`

不要再次询问用户使用哪个主题。

## 2. 内容处理总原则

1. 只做排版，不改写、不删减、不补充文章内容。
2. 严格保留原文自然段、小标题、列表、引用、加粗及内容顺序。
3. 不自行重新分段、合并段落或调整结构。
4. 不新增原文不存在的目录、导语、总结、`SECTION`、A/B/C 索引、阅读路径、关键议题或其他信息层级。
5. 文章标题不进入正文 HTML，由用户填写到微信公众号后台标题栏。
6. 公众号摘要不进入正文 HTML，由用户填写到微信公众号后台摘要栏。
7. 文章底部固定公司介绍模板不参与排版，由用户最后在微信公众号后台插入。

内容保真优先于 `SKILL.md` 中的自动章节编号、英文标签、目录提取、引言提炼、总结、作者签名、互动 CTA 等智能处理；原文没有的内容一律不得新增。

### 可见文字零改写与交付前校验

最终排版中的所有可见文章文字必须与用户提供的原文逐字一致。排版只允许改变 HTML 标签、字号、字重、颜色、行距、间距、对齐方式，以及卡片、引用、列表等视觉结构；不得增加解释、过渡、总结、导语、小标题、编号、提示语或标签，也不得改写、润色、缩写、扩写、合并、拆分或补全原文。

只有以下固定展示转换例外：

- `【引言】`、`【正文】`、`【说明】`、`【信息来源】` 是控制标记，最终不显示。
- `【图片来源X】具体来源` 可显示为 `图片来源：具体来源`，其中具体来源必须逐字不变。
- 说明区域允许固定显示 `说明：`。
- 信息来源区域允许固定显示 `信息来源：`。
- 引言左上角的蓝色装饰双引号是纯视觉元素，不计入正文文字。

交付前必须分别提取引言、正文、说明、信息来源的原文与最终 HTML 可见文本；去除 HTML 标签、上述控制标记、允许的固定展示标签和纯视觉装饰后逐段比较。必须确认无新增、无删除、无替换、无顺序变化；存在任何不一致时不得交付，应先修正并重新检查。

## 3. 引言规则

用户会单独提供 `【引言】`。

- 有内容时，将其作为正文开头引言，调用 blue-white 正式引言组件。
- 必须保留 blue-white 已固化的蓝色装饰双引号；该双引号是主题固定视觉元素，不属于正文文字。
- 没有内容时，视为本篇没有引言，直接从正文第一段开始；不生成引言卡或装饰双引号。
- 不自行生成引言。
- 不从正文中提取引言。
- 不把公众号摘要转换或复制成引言。
- 不改写、删减或补充用户提供的引言。
- 引言正文仍以黑色为主；可从原文已有加粗内容或承担核心判断的短语中选择极少数，使用品牌蓝 `#1E5876` 做行内强调。
- 每篇引言通常只强调 `1–2` 个短语，不整段变蓝，不使用大量高亮，不新增或改写任何文字。

## 4. 正文规则

用户会单独提供 `【正文】`。

- 严格按用户提供的正文内容和自然段排版。
- 不重新分段。
- 不合并段落。
- 不调整小标题顺序。
- 不修改加粗、列表、引用等原有结构。
- 使用正式 blue-white 主题已保存的正文参数和组件规则。

### 轻组件优先与组件触发

内容保真约束文字和顺序，不限制对原文已有结构进行正常的视觉判断。正文始终是主体，组件只做辅助，并按以下优先级使用：

1. 第一优先：普通正文，以及行内加粗、品牌蓝和必要的轻量下划线。
2. 第二优先：原文明示的小标题、列表、引用、图片、表格等结构。
3. 第三优先：8a、8c、8d、9a、9b 等卡片或容器组件；只有原文存在明确结构信号，或用户明确要求时才使用。

article-type recipe 只确定本篇可以优先考虑的组件集合，不是必须逐项使用的组件清单。不得为了满足 recipe 主动寻找句子套入 8a、8d、9a、9b 等容器。

- 原文已有的独立一级小标题，默认使用黑色粗体标题和下方蓝色细线；不加左侧蓝色竖线，不自动编号，不加英文标签，不新增标题文字。不得混用组件 5 与组件 6b。
- 明确 Markdown 引用 `>` 可以使用 8a；用户明确要求结论卡或引用卡时也可以使用 8a。8d 仅在用户明确要求独立金句或居中分隔时使用。
- 普通加粗句、结论句、重点句、箭头路径句默认不得自动使用 8a、8d、9a 或 9b。
- `境内公司 → 香港公司 → 印尼工厂` 一类路径文字仍按正文处理，可用加粗或品牌蓝轻量强化，不因箭头自动转为流程模块、居中模块或卡片。
- “先说结论”等普通重点内容默认保持正文结构，只做行内加粗、品牌蓝等轻量强化，不自动升级为浅蓝卡片或结论卡。

### 行内轻量强调节奏

普通正文保持黑色为主，只在原文已有重点关系清晰时使用组件 7 的行内样式。强调依据按以下顺序判断：

1. 原文已有的 `**加粗**`。
2. 原文已有的独立重点句。
3. 数字、比例和时间节点。
4. 关键业务名词。
5. 已经明确表达判断的关键短语。

可使用品牌蓝 `#1E5876`、普通粗体、品牌蓝粗体和轻量蓝色下划线。语义判断只决定原文中哪一段连续文字使用哪一种行内样式，不得改变文字、拆并段落或新建信息层级。

- 不要求每段都有强调；没有明确重点的段落保持普通正文。
- 单个有重点的段落通常只强调 `1–2` 个短语，避免整段变蓝或整段加下划线。
- 蓝色加粗只用于少量核心锚点；浅蓝下划线用于关键数据、业务名词和判断短语。
- 行内强调不得包裹成独立 section、卡片、引用块、流程块或提示块。
- `【说明】` 与 `【信息来源】` 不参与行内重点判断，继续使用固定弱化样式。

## 5. 配图占位规则

正文中的 `【配图1】`、`【配图2】`……属于人工插图定位标记。

严格使用 `references/theme-blue-white.md` 已正式固化的配图占位规则：

- 不生成图片。
- 保留配图定位位置。
- 不自行改变配图顺序。
- 不增加无关的配图占位。
- 只显示居中的浅灰定位文字；不做胶囊按钮、大框、背景或附加说明文字。

实际图片由用户另外生成，并在微信公众号后台手动插入。

## 6. 动态图片来源规则

如果正文中出现 `【图片来源X】具体来源内容`，严格使用 blue-white 已固化的图片来源规则。来源文字是动态的，以用户当次提供内容为准。

例如：

- 输入 `【图片来源1】国家发展改革委官网`，最终显示 `图片来源：国家发展改革委官网`。
- 输入 `【图片来源2】香港公司注册处`，最终显示 `图片来源：香港公司注册处`。

必须遵守：

- 不自行修改来源文字。
- 不补充来源。
- 不猜测来源。
- 没有提供时不生成图片来源区域，也不预留位置。
- `【图片来源X】` 仅为控制标记，最终 HTML 不显示该标记本身。

## 7. 说明规则

用户会单独提供 `【说明】`。

如果有内容：

- 放在正文结束之后、信息来源之前。
- 字号为 `13px`。
- 字体颜色为 `#747B84`。
- “说明：”加粗，其余文字保持正常字重。
- 不使用品牌蓝强调。
- 无背景、无卡片、无边框、无左侧竖线。
- 不进入 8c、9a、9b 等语义卡片判断。
- 不改写、删减或补充说明内容。

如果为空：

- 不生成说明区域。
- 不自行增加免责声明、风险提示或其他说明。

## 8. 信息来源规则

用户会单独提供 `【信息来源】`。

如果有内容：

- 放在说明之后；如果没有说明，则直接放在正文结束之后。
- 字号为 `12px`。
- 字体颜色为 `#9298A1`。
- “信息来源：”可轻微加粗，其余文字保持正常字重。
- 标题同样使用 `#9298A1`，不使用醒目的品牌蓝。
- 不使用品牌蓝强调。
- 无背景、无卡片、无边框。
- 不参与正文重点组件判断。
- 多个来源严格保持用户提供的顺序。
- 不自行增加、删除、修改或推断来源。

如果为空，不生成信息来源区域。

## 9. 图片来源与信息来源必须区分

- `【图片来源X】`：只对应某一张具体图片，显示在该图片下方。
- `【信息来源】`：对应整篇文章引用的政策、公告、数据、报告、官方资料等依据，位于文章末尾。

两者不得合并，也不得互相替代。

## 10. 默认输出

每次微信公众号排版默认生成：

1. 微信公众号正文 HTML（排版流程需要时生成）。
2. 带“复制到公众号”按钮的完整预览 HTML。
3. 微信公众号兼容性检查。

### 日常交付位置与入口

- 预览 HTML 必须直接生成在 `/workspace/`，文件名使用清晰的文章标识并以 `_预览.html` 结尾。
- 不把 `/workspace/outputs/` 作为日常预览 HTML 的主要交付位置。
- 最终回复必须直接引用 `/workspace/` 下的预览 HTML，使用可点击文件链接；该链接是用户日常查看和复制排版的主要入口。
- 用户点击链接后，应能在 Codex 右侧直接打开完整 blue-white 排版预览，并使用页面顶部的“复制到公众号”按钮。
- 预览页必须保留移动端 viewport 与手机端适配，并由 `scripts/wrap_preview.py` 基于已通过兼容性检查的干净正文 HTML 生成。
- 正文 HTML 可以同时生成在 `/workspace/` 作为兜底，但主要交付入口始终是可点击的预览 HTML。
- 兼容性检查针对预览页中实际复制的干净正文 HTML 执行；必须达到 `0 ERROR` 后才能交付。
- 交付前必须完成第 2 节规定的可见文本逐段一致性检查，并确认无新增、删除、替换或顺序变化。
- 文章正文 HTML、预览 HTML 和测试文件均是临时工作文件，只能放在仓库外的 `/workspace/`，不得提交到 GitHub、不得进入正式仓库，也不得影响仓库的 `git status`。

完成后只需简要告知：

- 使用主题。
- 是否有引言。
- 是否有说明。
- 是否有信息来源。
- 兼容性检查结果。

同时提供 `/workspace/` 下预览 HTML 的可点击文件链接，不必把正文 HTML 作为主要入口。

不要每次重复解释完整排版规则。
